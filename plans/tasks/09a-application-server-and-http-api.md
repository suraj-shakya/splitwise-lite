## Goal

A single Python process serves the static shell in `app/` and a small JSON API on the same
origin, turns a session cookie into an acting member, and refuses everything else. A
flatmate can open `http://localhost:8000`, sign up, sign in, and see that they are signed
in. Tasks 10, 11 and 12 then build screens against a fixed list of endpoints and a fixed
error contract, and neither picks a framework, invents a cookie attribute, nor decides what
a 404 means.

## The framework decision

**Decided here: Flask. The engineer implements this decision; they do not re-open it, and
they do not evaluate alternatives.**

The reasoning, on the record:

* The store is synchronous `sqlite3`. `EventStore`'s docstring says one store owns one
  connection, that it is not thread safe, and that "two stores on the same file is a
  supported arrangement", which is what WAL and the 5 second busy timeout are for. Every
  domain function is an ordinary blocking call. A threaded, synchronous WSGI application is
  therefore the shape that matches what already exists, and an async framework would mean
  either a thread pool wrapper around every store call or an async SQLite driver, both of
  which are cost with no benefit at flat scale.
* `scripts/serve.py` already runs a `ThreadingHTTPServer`, so threaded and synchronous is
  also the shape the repo already runs.
* Flask is one declared dependency that installs cleanly here (verified: Flask 3.1.3 plus
  werkzeug, jinja2, itsdangerous, markupsafe, click and blinker), it needs no code
  generation, no schema layer, no ORM and no build step, and its test client exercises the
  whole request path without binding a socket, which keeps the suite free of ports and
  threads.
* The user chose it deliberately after being shown the alternatives.

The one thing to hold onto: **Flask is a dependency of `web.py` and of nothing else.** The
domain layer stays framework free and importable with Flask absent. That is a tested
property, not an aspiration, and it is what keeps this decision reversible.

## The dependency change, exactly

This is the repo's first runtime dependency. Every earlier task refused one, so this is the
edit that has to be precise.

`pyproject.toml` becomes:

    dependencies = ["flask>=3.0,<4"]

    [dependency-groups]
    dev = ["pytest>=8.0,<10"]

* **Flask is capped below 4.** `>=3.0` alone resolves to the same 3.1.3 that was verified
  here, so the cap changes nothing today. It means a Flask 4 with a changed request or
  cookie API arrives because somebody chose it, not because an unrelated `uv sync` re-solved
  the graph.
* **pytest is capped below 10, and its floor stays at 8.** Re-resolving the lock for Flask
  also moves pytest from 8 to 9.1.1, because the pin is `>=8.0`. The suite passes under 9,
  so nothing is broken, but a major test-runner upgrade arriving as a side effect of adding
  a web framework is exactly the drift a lockfile is meant to prevent. The floor stays at 8
  because nothing in the suite needs 9 and forcing an upgrade on a contributor buys nothing.
  The cap is the deliberate part: pytest 10 is somebody's decision.
* **Installation is `uv sync` and nothing else.** Never `pip install`, never
  `uv pip install`, never `uv add`. `.claude/hooks/guard-deps.hs.sh` blocks the ad hoc
  route, and CLAUDE.md makes the declared-then-synced order the rule.
* `uv.lock` is regenerated by that `uv sync` and committed in the same commit as the
  `pyproject.toml` edit. A lockfile that disagrees with the manifest is the failure the rule
  exists to prevent.

### The guard test that will fail, and exactly how it changes

`tests/test_store.py::test_the_project_still_declares_no_runtime_dependency` asserts
`manifest["project"]["dependencies"] == []` and
`manifest["dependency-groups"] == {"dev": ["pytest>=8.0"]}`. It will fail. The task 6
reviewer predicted it on PR #23, so this is a sanctioned edit, not collateral damage.

**It is narrowed, not deleted, and it is narrowed in two directions at once.**

1. The manifest test is renamed to `test_the_project_declares_exactly_one_runtime_dependency`
   and asserts the two new lists exactly. It still bites: a second runtime dependency, a
   loosened cap or a dev tool added quietly all fail it, which is the property the original
   was guarding. Only the "zero" became "exactly one, and it is Flask".
2. A new test is added immediately below it, because the manifest string is now the weaker
   half of the guard. It parses every `.py` file under `src/splitwise_lite/` with `ast` and
   asserts that no module except `web.py` imports `flask`, `werkzeug`, `jinja2`,
   `itsdangerous`, `markupsafe`, `click` or `blinker`, and that `web.py` imports `flask`
   only, never a transitive package directly. That is the real property: one module knows
   about the framework, the declared dependency tells the whole truth, and the domain layer
   can still be imported, tested and reused with Flask uninstalled.

Both live in `tests/test_store.py`, next to each other, so somebody deleting one sees its
partner. They are the only pre-existing tests in that file this task touches.

## How it runs, and what happens to `scripts/serve.py`

**Decided here: Flask serves `app/` itself, and `scripts/serve.py` survives as the one run
command, rewritten to start the Flask app.** There is exactly one way to run the product
after this task.

* Keeping a second, static-only server would keep a trap: the shell now calls the API, so a
  server that cannot answer it serves a broken app while its own tests pass.
* Rewriting the script rather than deleting it keeps the run command's shape, keeps
  `tests/test_dev_server.py` pointed at a real file, and keeps the two facts that script
  already encodes and that still matter: it binds `127.0.0.1` only, and it resolves `app/`
  from its own location rather than the working directory.
* **The Windows MIME trap comes with it.** Flask's `send_from_directory` guesses content
  types with `mimetypes`, which reads the Windows registry, where `.js` is commonly mapped
  to `text/plain`. That is the exact failure `scripts/serve.py` was written to avoid, and
  moving to Flask does not fix it. `web.py` therefore carries the same explicit extension
  map and sets `Content-Type` from it, and never relies on `mimetypes`.

The run command becomes:

    uv run python scripts/serve.py --store ledger.sqlite3

`--store` is required, with no default, no environment variable and no directory creation,
matching `scripts/setup_group.py`. It still serves on `http://localhost:8000` and still
binds `127.0.0.1`.

Production is not chosen here. `create_app` returns a plain WSGI application that any
server can mount, and picking one (with the further dependency that implies) is a
deployment task. Werkzeug's development server is not it, and the run command's own output
says so.

## Session transport: the cookie

Task 7 built the session and named every transport decision it was deferring. Here they
are, all of them.

| Attribute | Value | Why |
|---|---|---|
| Name | `sl_session` | Not `session`, which is Flask's own signed cookie name. Nothing here uses `flask.session`, and a collision would make two unrelated things look like one. |
| Value | The raw token from `IssuedSession.token`, unchanged | 43 URL-safe characters. It is not signed, not encrypted and not encoded again: it is 256 bits of randomness whose only copy on the server is a SHA-256 hash. |
| `HttpOnly` | Always on | No script in `app/` ever needs the token, so script access is pure downside. |
| `Secure` | Required argument to `create_app`, no default | See below. |
| `SameSite` | `Lax` | `Strict` would sign the user out of the first navigation from any link, including a chat message from a flatmate. `Lax` still blocks every cross-site POST, which is the CSRF surface that matters. `None` would invite cross-site use and is refused. |
| `Path` | `/` | The shell and the API share one origin and one root. |
| `Domain` | Not set | Host-only. There is no subdomain and nothing may write this cookie from one. |
| `Max-Age` | `int((session.expires_at - now).total_seconds())` | Derived from the row, never a second constant. Today that is 2592000 seconds, because `accounts.SESSION_LIFETIME` is 30 days. |

**`Secure` has no default, deliberately.** `create_app(*, store_path, secure_cookies)`
takes it as a required keyword argument, so every caller states it and nobody gets it wrong
by omission. `scripts/serve.py` passes `False` and prints one warning line saying so;
that is safe only because it binds loopback. A deployment passes `True`. Making it a silent
default that flips on the request scheme would be the same class of mistake task 7 forbade
when it banned a `try/except` fallback to a weaker KDF: a security control that quietly
turns itself off is worse than one that is off on purpose.

**The 30 day lifetime lives in the row, not the cookie.** `Max-Age` is a hint to the
browser. The server compares `now` against `expires_at` on every request through
`accounts.authenticate`, so a cookie that outlives its row authenticates as invalid. There
is no sliding renewal and no re-issue on a normal request, matching task 7's decision: a
user signs in again once a month.

**An invalid token gets 401 and the cookie is cleared in the same response.** Unknown,
expired, malformed, over-long and deleted all arrive as `SessionInvalid` and are one
response, because "you were signed out, sign in again" is one screen. Clearing the cookie
matters: without it a stale token sits in the browser producing a 401 on every request
forever, and the user has no way to get rid of it.

**Logout deletes the row and clears both cookies, and never fails.** `DELETE /api/session`
returns 204 whether the cookie was valid, expired or absent. `accounts.log_out` is already
idempotent, and a person whose session died still needs the sign-out button to work. The
clearing `Set-Cookie` repeats `Path`, `SameSite`, `Secure` and `HttpOnly` exactly, because a
delete whose attributes do not match the original misses.

## CSRF

Flask ships none. **Decided here: three cheap gates in one `before_request` hook, all
standard library, no new dependency and no approval needed.** Applied to every
state-changing method (`POST`, `PUT`, `PATCH`, `DELETE`) on every `/api` path, with no
per-endpoint exemptions.

1. **`Content-Type` must be `application/json`** (parameters such as `; charset=utf-8` are
   ignored). A cross-site HTML form can only send `application/x-www-form-urlencoded`,
   `multipart/form-data` or `text/plain`. Anything else forces a CORS preflight, and this
   app answers no preflight and sends no CORS header, so the browser blocks it. This gate
   alone stops the classic form attack, and it costs nothing because the API is JSON only.
2. **Double-submit token.** The app sets a non-`HttpOnly` `sl_csrf` cookie holding 256 bits
   from `secrets.token_urlsafe(32)`. Every state-changing request must repeat it in an
   `X-CSRF-Token` header, compared with `hmac.compare_digest`. An attacker's page cannot
   read the cookie, so it cannot produce the header.
3. **`Origin` must match**, when the browser sent one. Present and different is a refusal;
   absent is not a refusal on its own, because gates 1 and 2 already stand and some
   same-origin requests omit it. `fetch` always sends it for the requests this app makes.

Why not a library: `flask-wtf` drags WTForms in for a form stack this product does not have,
and every alternative is a second dependency for a comparison of two random strings.
**Do not add `flask-wtf`, `flask-seasurf`, `flask-security` or any token library. If the
engineer believes one is needed, stop and get the user's approval before writing code.**
`itsdangerous` being installed transitively is not permission to use it.

The token is issued on the response to any safe request (`GET`, `HEAD`) that arrived without
the cookie, so loading the shell always yields one and the login POST can carry a header
before any session exists. It is rotated on login and cleared on logout. It is unrelated to
the session token and never derived from it, and it is not stored server side: it is not a
credential, it is a proof that the request came from a page on this origin.

A failed gate is **403**, not 401. The caller may well be authenticated; the request is not
trusted.

## Login rate limiting

Also deferred here by name. **Decided here: an in-process, in-memory, fixed-window failure
counter held on the app object, guarded by a `threading.Lock`. No new table, no schema
version 3, no cache server and no dependency.**

Where the state lives, and why not SQLite:

* Putting a counter in the store means a write on the unauthenticated login path, which
  hands an attacker an unbounded write against the one SQLite writer, plus disk growth, plus
  a lock the honest logins then queue behind. It also means `SCHEMA_VERSION` 3 for
  bookkeeping that is not ledger data, when tasks 6, 7 and 9 all treated the schema as
  something you touch for a reason.
* v1 runs as one process on one small host. An in-process limiter is therefore complete for
  the deployment that exists, and its limits are stated in one place a reviewer can read.
* The gap is recorded rather than hidden: a restart clears the counters, and two processes
  double the allowance. Both are acceptable at flat scale and neither is acceptable
  silently.

**The real reason to limit is CPU, not guessing.** scrypt at `DEFAULT_SCRYPT_PARAMS` costs
64 MiB and hundreds of milliseconds per attempt, so an unlimited login endpoint is a
denial-of-service amplifier before it is a password oracle. The limiter therefore refuses
**before** the KDF runs, which is the whole point of it.

Shape:

* Two independent buckets, both counting failures only in a 15 minute fixed window: at most
  10 per normalised email address, at most 30 per client IP. Both must be under their limit.
* Per-email alone would let one attacker lock a flatmate out. Per-IP alone would let a
  distributed attacker through. Neither bucket is a lockout: the window expires by itself,
  because task 7 pointed out that a sticky lockout in a product with no password reset flow
  locks a flatmate out permanently.
* A successful login clears that email's bucket and leaves the IP bucket alone, so holding
  one valid account does not reset an attacker's budget.
* Signup is limited by IP on the same terms and with its own bucket. It runs the same KDF
  and it writes rows.
* The client is `request.remote_addr` and nothing else. `X-Forwarded-For` is spoofable, and
  trusting a header a client controls is worse than having no per-IP bucket at all. Behind a
  reverse proxy every request looks like one address, which is why the IP limit is 30 rather
  than 10: a four-person flat behind one NAT never reaches it. Whoever deploys behind a
  proxy owns configuring a trusted-proxy story, and that is out of scope here.
* Each bucket map is capped (1024 emails, 4096 addresses) and evicts its own oldest entry
  when full, so the limiter cannot grow without bound and address churn cannot evict the
  email bucket for the address being attacked.
* Over the limit is **429** with `Retry-After` in whole seconds and a message that names
  neither the address nor whether it exists.

## The `DomainError` to HTTP status mapping

Five modules put their errors under one `DomainError` family precisely so this is one
mapping in one place. It is a module-level dict in `web.py`, keyed by exception class,
resolved by walking the raised exception's MRO so a subclass added later cannot fall through
to 500 by accident.

| Exception | Status | `code` |
|---|---|---|
| `NotAuthenticated` (web) | 401 | `not_authenticated` |
| `accounts.SessionInvalid` | 401 | `session_invalid` |
| `accounts.AuthenticationFailed` | 401 | `authentication_failed` |
| `web.CsrfFailed` | 403 | `csrf_failed` |
| `groups.MemberNotLinked` | 403 | `member_not_linked` |
| `store.RecordNotFound` | 404 | `record_not_found` |
| `accounts.EmailAlreadyRegistered` | 409 | `email_already_registered` |
| `store.DuplicateRecord` | 409 | `duplicate_record` |
| `store.ConstraintViolated` | 409 | `constraint_violated` |
| `groups.GroupMismatch` | 409 | `group_mismatch` |
| `groups.MemberAlreadyLinked` | 409 | `member_already_linked` |
| `groups.UserAlreadyLinked` | 409 | `user_already_linked` |
| `web.TooManyAttempts` | 429 | `too_many_attempts` |
| `web.MalformedRequest` | 400 | `malformed_request` |
| `accounts.InvalidEmail` | 400 | `invalid_email` |
| `accounts.InvalidPassword` | 400 | `invalid_password` |
| `money.InvalidAmount` | 400 | `invalid_amount` |
| `money.InvalidCurrency` | 400 | `invalid_currency` |
| `money.CurrencyMismatch` | 400 | `currency_mismatch` |
| `split.InvalidSplit` | 400 | `invalid_split` |
| `store.InvalidRecord` | 400 | `invalid_record` |
| `store.AmountTooLarge` | 400 | `amount_too_large` |
| `groups.NoGroupConfigured` | 503 | `no_group_configured` |
| `groups.AmbiguousGroup` | 503 | `ambiguous_group` |
| `accounts.PasswordHashInvalid` | 500 | `internal_error` |
| Every other `DomainError`, and every non-`DomainError` | 500 | `internal_error` |

Three of those rows are worth their reasoning:

* **`NoGroupConfigured` and `AmbiguousGroup` are 503, not 404 and not 500.** Neither is
  anything a client can fix by changing its request, and both are fixed by running
  `scripts/setup_group.py`. 503 with a message naming that command is the honest answer for
  a server that is not set up yet.
* **`PasswordHashInvalid` is a 500.** Task 7 was explicit that a corrupt stored hash is
  database damage, and reporting it as a wrong password would hide that behind a support
  ticket about a forgotten password.
* **`ConstraintViolated` is 409, not 400.** The request parsed; the write disagreed with a
  rule the database enforces. The endpoints validate ids against the roster before writing,
  so it should be unreachable, and if it is reached it deserves to look like a conflict in
  the log rather than a typo.

The two inherited notes from task 9, carried here verbatim in effect:

* **A losing racer in a concurrent signup surfaces `DuplicateRecord` from the store rather
  than `EmailAlreadyRegistered` from `accounts.py`.** Both map to 409 in the table, and the
  signup handler additionally catches `DuplicateRecord` and answers with the same
  `email_already_registered` body, because a losing racer and a plain duplicate are the same
  situation for the person typing.
* **A losing link racer can surface `DuplicateRecord` rather than `MemberAlreadyLinked` or
  `UserAlreadyLinked`.** No endpoint here links anybody, so this task cannot hit it; all
  three are in the table anyway, at 409, so the task that adds a link endpoint inherits a
  mapping rather than a gap.

Body shape, for every error, at every status:

    {"error": {"code": "record_not_found", "message": "..."}}

For 4xx the `message` is `str(error)`: those strings were written deliberately in this repo
for a person to read, and task 7 already guarantees none of them contains a password. For
5xx the `message` is one fixed generic string and the real exception goes to the log with
its traceback, because a 500 message can carry a file path, a SQL fragment or a stored hash.

## The endpoints

Enough for tasks 10, 11 and 12 and no more. Every path is under `/api`, every request and
response body is JSON, and money crosses the wire only as a formatted string.

| Method | Path | Requires | Success |
|---|---|---|---|
| `POST` | `/api/signup` | nothing | 201 |
| `POST` | `/api/session` | nothing | 200, sets both cookies |
| `GET` | `/api/session` | a valid session | 200 |
| `DELETE` | `/api/session` | nothing | 204, clears both cookies |
| `GET` | `/api/members` | session and a linked member | 200 |
| `GET` | `/api/expenses` | session and a linked member | 200 |
| `POST` | `/api/expenses` | session and a linked member | 201 |
| `GET` | `/api/balances` | session and a linked member | 200 |

**A signup endpoint is required, not optional.** `scripts/setup_group.py link` resolves a
user through `store.get_user_by_email`, so the user must already exist, and no CLI creates
one. Without `POST /api/signup` no account can ever exist and nobody can ever be linked.

**Money crosses the wire as a formatted string, never as a number and never as cents.**
`format_amount` produces it and `parse_amount` consumes it, so the two existing edges stay
the only ones. This is what makes task 8's "no money formatting in `app/`" rule survivable:
the front end is given nothing it could do arithmetic on. A JSON number where an amount is
expected is a 400.

### `POST /api/signup`

    {"email": "sam@example.com", "display_name": "Sam", "password": "correct horse ..."}

201 with `{"user": {"id": ..., "email": ..., "display_name": ...}}`. **It creates no
session.** Task 7 decided signup issues none, and keeping one place that mints a session is
worth the client's second request. The client calls `POST /api/session` next.

### `POST /api/session`

    {"email": "sam@example.com", "password": "..."}

200 with the session view below, plus `Set-Cookie` for `sl_session` and a rotated `sl_csrf`.

### `GET /api/session`

200 with the session view:

    {
      "user":   {"id": "...", "email": "sam@example.com", "display_name": "Sam"},
      "group":  {"id": "...", "name": "Flat 3", "currency": "AUD"},
      "member": {"id": "...", "display_name": "Sam"}
    }

`member` is `null` when nobody has linked this user yet. This is the one endpoint that
answers 200 for an unlinked user, and it exists so the shell can render "you are signed in,
ask whoever set the flat up to link you" rather than a bare error.

### `DELETE /api/session`

204, empty body, both cookies cleared.

### `GET /api/members`

    {"members": [{"id": "...", "display_name": "Sam"}, ...]}

In `store.list_members` order, which task 9 fixed to roster order. It carries no
`user_id`, no email address and no "is linked" flag: task 9 decided an unlinked member is a
full member that nothing filters, greys out or marks pending, and leaving the flag out means
a screen cannot accidentally start doing it. It also means a screenshot of the roster is not
an account list.

### `GET /api/expenses`

    {
      "currency": "AUD",
      "expenses": [
        {
          "id": "...",
          "description": "Milk",
          "amount": "12.50",
          "payer_id": "...",
          "created_by": "...",
          "created_at": "2026-09-05T09:00:00.123456+00:00",
          "allocations": [{"member_id": "...", "amount": "4.17"}, ...]
        }
      ]
    }

Newest first. Allocations ride along, so task 11's tap-to-open detail needs no second
request and no per-expense endpoint. Display names do not: one roster call covers every
screen, and duplicating names into every expense is how two spellings of one member end up
on one page.

### `POST /api/expenses`

    {
      "description": "Milk",
      "amount": "12.50",
      "payer_id": "...",
      "split": {"mode": "equal",  "member_ids": ["...", "..."]}
    }

`split` is one of three shapes, matching `split.py` exactly:

* `{"mode": "equal", "member_ids": [...]}` for equal across all and equal across a subset,
  which are the same call with a different list.
* `{"mode": "weight", "weights": {"<member id>": 2, ...}}`, integer weights.
* `{"mode": "exact", "amounts": {"<member id>": "8.00", ...}}`, amounts as strings.

201 with `{"expense": {...}}` in the same shape as a feed entry. The currency is the
group's and cannot be named in the body. `created_by` is the acting member and cannot be
named in the body. `id` comes from `new_id()` and `created_at` from the server clock, and
neither can be named in the body. `payer_id` may be any member of the group, because
recording that a flatmate paid is a normal entry, not an impersonation.

### `GET /api/balances`

    {
      "currency": "AUD",
      "net": [{"member_id": "...", "amount": "12.50", "direction": "owed"}, ...],
      "transfers": [{"from_member_id": "...", "to_member_id": "...", "amount": "12.50"}, ...]
    }

`net` covers every member of the group in roster order, including members the ledger has
never seen, using `Balances.net_for`, which is total by design. `direction` is `"owed"`
when they are owed money, `"owes"` when they owe it and `"settled"` at zero, and `amount` is
always the non-negative magnitude, so no client ever has to parse or render a minus sign.

Transfer provenance (`payer_debts` and `receiver_credits`) is **not** in this payload. Task
13 owns the drill-down and adds it there, which is a widening of one response object rather
than a new endpoint.

## Reading the ledger requires a member link

Task 9 recorded this as undecided: "Whether an unlinked user may *read* the ledger is not
decided here. It is a request layer question, and the request layer does not exist yet."
This is the request layer.

**Decided here: no. A signed-in user with no member row in the group may not read the
ledger.** Every `/api` endpoint except `POST /api/signup`, `POST /api/session`,
`GET /api/session` and `DELETE /api/session` requires both a valid session and a linked
member, and answers 403 `member_not_linked` otherwise.

The reasoning is task 7's own safety argument. Signup is unverified, the spec cuts email
verification, and the only thing that makes an unverified signup harmless is that "signup
grants nothing at all: no group, no member link, no data". If an unlinked account could read
the feed, that sentence stops being true and any stranger who signs up can read the flat's
spending. Membership of the group is the only authorisation this product has, so it is the
one that gates reads.

Authentication is checked **before** group resolution, so an unauthenticated caller against
a store with no group gets 401 rather than a 503 that tells them how the server is
configured.

## What task 8's contract becomes

Task 8's criteria say no file under `app/` calls `fetch`, `XMLHttpRequest`, `EventSource` or
`WebSocket`, or references an API path, and `tests/test_web_shell.py::test_no_shell_file_calls_a_back_end`
enforces it over every shell file. Those criteria are on `master` and this task changes
them. Stated plainly, because tasks 7 and 9 both made this class of cross-task test edit and
both were scrutinised hard:

* **Task 9a owns the loosening.** Not task 10, 11 or 12. If three screen tasks each loosened
  it a little, there would be three network chokepoints and three answers to a 401.
* **It is narrowed to one file, not removed.** `fetch(` and the string `/api` become legal
  in `app/api.js` only, plus `/api` in `app/sw.js` so the worker can refuse to cache it.
  `app/app.js` and every other shell file still must not contain either.
  `XMLHttpRequest`, `EventSource` and `WebSocket` stay banned everywhere, unchanged: nothing
  here needs them.
* **A new test is added alongside it asserting the narrowed rule still bites**, exactly as
  task 7 did when it narrowed the `DELETE FROM` rule: `app/app.js` contains no `fetch(`, and
  `app/api.js` is the only file under `app/` that builds an API URL. The test is renamed to
  `test_only_the_api_client_calls_the_back_end`, so its name states the property it now
  guards.
* Task 8's other independence rules **do not** change. No file under `app/` does money
  formatting, cent arithmetic, split logic or allocation maths, and the string-only money
  contract above is what makes that easy to keep.

**This task also builds the auth gate**, because no task owns a sign-in screen: task 7 put
it out of scope, task 8's three screens are feed, add and balances, and tasks 10 to 12 are
each one of those. Without it, nothing can obtain a cookie and the API is unreachable from
the product. It is deliberately not a fourth route: it is a section shown in place of
`<main>` and the tab bar, so `ROUTES` in `app/app.js` still holds exactly three entries and
task 8's "the router owns the route-to-screen mapping" criterion survives untouched.

**What the front end does with a 401.** `app/api.js` is the only place that knows: it clears
its cached session view, invokes one callback, and the boot code shows the gate. It does not
retry, does not redirect, and does not loop. A **403 `member_not_linked`** shows a different
message, "nobody has linked you to a member yet", because retyping a password would not fix
it. A **network failure** (offline, server down) shows a third message and never the sign-in
gate: prompting for a password on a page that cannot send it is how a person ends up typing
their password into nothing, repeatedly.

## What is deliberately not defended against in v1

Each of these is a recorded decision. If any is unacceptable, that is a conversation to have
before an engineer starts.

* **TLS.** There is none, and the app must not be reachable beyond loopback until somebody
  writes one. The session cookie is a bearer token, and plain HTTP on a shared network hands
  it to anyone listening. `secure_cookies=True` is meaningless without TLS in front, and the
  run command binding `127.0.0.1` is what contains this.
* **Deployment.** No production WSGI server, no process manager, no reverse proxy config, no
  container, no HSTS and no trusted-proxy handling. `create_app` returns a WSGI application
  and stops there.
* **A restart clears the rate limiter**, and two processes double every allowance. Stated
  above.
* **Password reset and email verification**, still cut. A flatmate who forgets their
  password has no route back, and the API adds none.
* **Signup email enumeration**, still open: signup says when an address is taken. Task 7
  recorded the reasoning and the bounded damage.
* **No audit trail of authentication.** No login history, no failed-attempt log beyond the
  in-memory counter, no record of who read what.
* **No per-request authorisation beyond membership.** Any linked member may write any
  expense and name any payer. There is no privileged user in a flat, per task 7, and the
  ledger is append-only, so a wrong entry is corrected by task 17 rather than prevented here.
* **No pagination on the feed.** A flat logs a few hundred expenses a year and
  `store.list_expenses` already returns them all. Adding paging now would be a second
  ordering contract to keep in step with the first, for a payload that is measured in
  kilobytes.
* **No caching, no `ETag`, no `If-None-Match`.** Every response carries
  `Cache-Control: no-store`. A stale balance is exactly the "looks authoritative while being
  wrong" failure the spec names as the product's largest risk.
* **No Content Security Policy.** It needs an inventory of every inline handler and style in
  the shell plus a nonce mechanism, and getting it half right silently breaks the app. The
  three cheap headers below are shipped instead, and CSP is named as a later task's work.
* **Running from an installed wheel.** `app/` is not packaged, so the app is served from a
  clone. `[tool.hatch.build.targets.wheel]` is not touched.

**The application factory and the store**

- `create_app(*, store_path, secure_cookies, app_dir=None)` returns a `flask.Flask`.
  `store_path` and `secure_cookies` are required keyword arguments and neither has a
  default.
- `secure_cookies` is a required `bool`. There is no code path that derives it from the
  request scheme, an environment variable or a debug flag.
- `store_path` is passed to `open_store` unchanged. There is no default path, no environment
  variable read and no directory created, matching task 6 and task 9.
- Passing `IN_MEMORY` raises immediately with a message saying why: a per-request connection
  to a private in-memory database is a fresh empty ledger every request.
- A store is opened per request through `flask.g` and closed in `teardown_appcontext`, so no
  handle outlives a request. This is the "two stores on one file" arrangement `EventStore`'s
  docstring calls supported, and it is what makes the threaded server safe against a store
  that is not thread safe. There is no module-level store, no singleton and no connection
  pool.
- A test asserts the store is closed after a request, including a request that raised, and
  that a file-backed store under `tmp_path` can be opened by the test alongside the app's own
  connection.
- `app_dir` defaults to the repo's `app/` resolved from `web.py`'s own location, never from
  the current working directory.
- `create_app` binds no socket and starts no server. Importing `web.py` does nothing beyond
  definitions.
- Two apps created in one process share no state: the rate limiter lives on the app, not in
  a module global. A test creates two apps and asserts exhausting one limiter leaves the
  other untouched.

**Serving `app/`**

- `GET /` returns `app/index.html` with status 200 and
  `Content-Type: text/html; charset=utf-8`.
- Static files are served from `app_dir` with content types read from an explicit
  `EXTENSIONS` map covering at least `.html`, `.css`, `.js`, `.json`, `.webmanifest`, `.png`
  and `.ico`. `mimetypes` is never consulted. An extension not in the map is served as
  `application/octet-stream`.
- `/app.js`, `/api.js` and `/sw.js` are served as `text/javascript; charset=utf-8`,
  `/manifest.json` as `application/json`, and `/icons/icon-192.png` as `image/png` with the
  PNG signature intact. These are the assertions that stop the Windows registry MIME map from
  making the app uninstallable, and they are why the map exists.
- The app defines no `/static` route: `Flask(..., static_folder=None)`, and
  `GET /static/anything` is a 404.
- Path traversal is refused: `GET /../pyproject.toml` and any encoded equivalent returns 404
  and never reads a file outside `app_dir`. A test covers at least two encodings.
- A missing static path returns 404 and does not fall back to `index.html`. Hash routing
  means every route requests the same document, so a catch-all would only hide typos.
- Every response, static and API alike, carries `Cache-Control: no-store`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` and
  `X-Frame-Options: DENY`.
- No response carries any `Access-Control-Allow-*` header. There is no CORS support and no
  CORS library, which is part of why the CSRF gates hold.

**Session transport**

- A successful `POST /api/session` sets `sl_session` to the raw token from
  `accounts.log_in`, with `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`, and
  `Max-Age` computed as `int((session.expires_at - now).total_seconds())`, which is exactly
  `2592000` under `accounts.SESSION_LIFETIME`. A test asserts the whole `Set-Cookie` header
  field by field.
- `Secure` is present on both cookies when `create_app` was given `secure_cookies=True` and
  absent when it was given `False`. A test covers both apps.
- The raw token appears in no log line, no error body and no response body. It appears only
  in the `Set-Cookie` header.
- `GET /api/session` with a live cookie returns 200 and the session view. It sets no new
  session cookie and extends nothing: there is no sliding renewal.
- An unknown, malformed, over-long, expired or logged-out token returns 401 `session_invalid`
  and the same response clears `sl_session` with `Max-Age=0` and matching `Path`, `SameSite`,
  `Secure` and `HttpOnly`. Each of those five cases has its own test.
- A request with no `sl_session` cookie at all returns 401 `not_authenticated` and clears
  nothing.
- Expiry is honoured at the boundary the way task 7 defined it: a request one microsecond
  before `expires_at` succeeds and one at `expires_at` returns 401.
- `DELETE /api/session` returns 204 and clears both cookies, whether the session was live,
  expired, already deleted or absent. It deletes exactly that session row and leaves the
  user's other sessions authenticating. A test with two sessions for one user proves it.
- A session issued before an operator linked the user resolves to the member on the next
  request. Nothing about the member is cached in the session or the cookie.

**CSRF**

- The app sets `sl_csrf` on the response to any `GET` or `HEAD` that arrived without it,
  including `GET /`, with `Path=/`, `SameSite=Lax`, `Secure` per the app's setting, and
  **not** `HttpOnly`, because the client must read it.
- Its value is `secrets.token_urlsafe(32)`. It is rotated on a successful login and cleared
  on logout. It is never derived from the session token and is never stored in the database.
- Every `POST`, `PUT`, `PATCH` and `DELETE` under `/api` requires all three gates, with no
  per-endpoint exemption: a `Content-Type` whose media type is exactly `application/json`, an
  `X-CSRF-Token` header equal to the `sl_csrf` cookie, and an `Origin` that matches this
  origin when the header is present.
- `application/json; charset=utf-8` is accepted; `text/plain`,
  `application/x-www-form-urlencoded`, `multipart/form-data` and a missing `Content-Type` are
  each 403 `csrf_failed`, and each has its own test.
- A missing header, a header that does not match the cookie, a missing cookie and a
  mismatched `Origin` are each 403 `csrf_failed`. A request with no `Origin` header at all is
  not refused on that ground.
- The comparison uses `hmac.compare_digest`. The source contains no `==` between a submitted
  CSRF token and a stored one.
- `GET`, `HEAD` and `OPTIONS` are never subject to the gates and never state-changing.
- Login and signup are subject to the gates like everything else, which is why the cookie is
  issued on the first safe request rather than at login.
- No CSRF library is added. `pyproject.toml` names `flask` and nothing else.

**Rate limiting**

- `RateLimiter` counts failures in a fixed window, is guarded by a `threading.Lock`, holds
  no more than 1024 email keys and 4096 address keys, and evicts its own oldest entry per map
  when full. It is unit tested directly, with an injected clock, never with `sleep`.
- `LOGIN_WINDOW` is 15 minutes, `LOGIN_LIMIT_PER_EMAIL` is 10 and
  `LOGIN_LIMIT_PER_ADDRESS` is 30. A test asserts those exact numbers, so changing them is a
  visible edit.
- The 11th failed login for one address in the window returns 429 with a `Retry-After`
  header in whole seconds. The 10th still runs normally.
- **A refused request never runs the KDF.** A test replaces `accounts.log_in` with a function
  that fails the test if called, and asserts the 429 still comes back.
- A successful login clears that email's bucket and leaves the address bucket untouched. A
  test proves the second half by exhausting the address bucket with failures for other
  addresses and asserting a correct password for a fresh address is still refused with 429.
- Only failures count. A test logs in correctly 50 times in one window and is never limited.
- The 429 message names neither the email address nor whether an account exists, and a test
  asserts it is byte-identical for a registered and an unregistered address.
- `POST /api/signup` is limited per address on the same window with its own bucket, and
  exhausting the login bucket does not exhaust the signup one.
- The client key is `request.remote_addr`. The source reads no `X-Forwarded-For`, no
  `X-Real-IP` and no `Forwarded` header, and `ProxyFix` is not installed.
- No table, no column and no schema change: `SCHEMA_VERSION` is still 2 and `_SCHEMA_SQL` is
  untouched. `tests/test_store.py`'s schema tests pass unchanged.

**The error contract**

- `ERROR_STATUS` maps exception classes to integer statuses exactly as tabulated above, and
  `ERROR_CODE` maps them to their string codes. A parametrized test walks every row.
- A test asserts every concrete `DomainError` subclass exported by `money.py`, `store.py`,
  `accounts.py`, `groups.py`, `split.py`, `balances.py`, `simplify.py` and `web.py` either
  appears in the table or is deliberately covered by the `DomainError` fallback, so a new
  domain error cannot silently become a 500 without somebody seeing this test.
- Lookup walks the raised exception's MRO, so a subclass of a mapped error inherits its
  status rather than falling to 500. A test defines a subclass and proves it.
- Every error response body is exactly `{"error": {"code": ..., "message": ...}}` with
  `Content-Type: application/json`, at every status including 404, 405 and 413.
- 4xx bodies carry `str(error)`. 5xx bodies carry one fixed generic message, and the real
  exception including its traceback goes to the application log. A test asserts the raised
  message does not appear in a 500 body and does appear in the log.
- An unhandled non-`DomainError` exception is a 500 in the same shape, and the response is
  not Werkzeug's HTML error page.
- `GET /api/nope` is a JSON 404, not the shell document. `PUT /api/session` is a JSON 405
  with an `Allow` header. A non-API path that does not exist is a plain 404.
- A request body over `MAX_BODY_BYTES` (65536) is a 413 in the same JSON shape, and the body
  is not buffered beyond the cap.
- Malformed JSON, a body that is not a JSON object, a missing required key, a key of the
  wrong JSON type and an unrecognised key are each 400 `malformed_request`, and the message
  names the key. `currency`, `created_by`, `created_at`, `id` and `now` in an expense body
  are unrecognised keys, which is how the client is prevented from naming any of them.
- No error message contains a password, a session token, a CSRF token, a password hash or a
  filesystem path. A test drives a failing signup, login and password-bearing malformed body
  and asserts the password string appears in no response body and no log record.

**Authentication and the member link**

- A parametrized test hits **every** endpoint and method in the table with no cookies at all
  and asserts the exact expected status for each: 401 for `GET /api/session`,
  `GET /api/members`, `GET /api/expenses`, `POST /api/expenses` and `GET /api/balances`; 204
  for `DELETE /api/session`; and for `POST /api/signup` and `POST /api/session` a 403 when
  the CSRF gates are unmet, or the endpoint's own answer when they are met. No endpoint is
  missing from that test, and adding a route without adding a row fails it.
- A second parametrized test hits every endpoint with a valid session for a user linked to no
  member. `GET /api/session` returns 200 with `"member": null`. `GET /api/members`,
  `GET /api/expenses`, `POST /api/expenses` and `GET /api/balances` each return 403
  `member_not_linked`. `DELETE /api/session` returns 204.
- The member requirement is the default. The endpoints exempt from it are one named tuple in
  `web.py`, and a test asserts that tuple holds exactly the four session and signup
  endpoints, so a new endpoint added without thought gets the locked-down behaviour.
- Authentication is checked before group resolution: an unauthenticated request against a
  store with no group returns 401, not 503. A test with an empty store proves it.
- A signed-in user against a store with no group gets 503 `no_group_configured` from
  `GET /api/session`, with a message naming the setup command.
- A store holding two groups gives 503 `ambiguous_group` naming both ids.
- The acting member is resolved per request through `groups.resolve_sole_group` and
  `groups.acting_member`. No group id and no member id is cached between requests, held in a
  module global or read from the cookie.

**Signup and login**

- `POST /api/signup` with a valid body returns 201 and `{"user": {...}}` carrying the id, the
  email and the display name, and no password field of any kind.
- It creates no session and sets no `sl_session` cookie. A test asserts a following
  `GET /api/session` is still 401.
- A duplicate address returns 409 `email_already_registered`. A test that forces the store to
  raise `DuplicateRecord` gets the **same** status and the same code, which is the concurrent
  signup race task 9 handed over.
- A bad address is 400 `invalid_email`, a short password 400 `invalid_password`, and a blank
  display name 400 `invalid_record`, each with the message the domain layer wrote.
- `POST /api/session` with the right password returns 200 and the session view. With a wrong
  password, an unknown address and a user with no credential row it returns 401
  `authentication_failed` with one identical message in all three cases, preserving task 7's
  guarantee that the response reveals nothing about which field was wrong.
- Signing in twice yields two distinct tokens and two live sessions, and both authenticate.
- Logging in rotates `sl_csrf`, and a request using the pre-login CSRF token is refused. A
  test proves the client recovers by re-reading the cookie.

**Members, expenses and balances**

- `GET /api/members` returns every member of the group in `store.list_members` order, with
  `id` and `display_name` only. A test asserts the exact JSON, including that no key named
  `user_id`, `email` or `linked` appears anywhere in the payload.
- `GET /api/expenses` returns the group's expenses newest first, ties broken by id
  descending, each with its allocations. A test seeds three expenses and asserts the exact
  ordered list of ids.
- A group with no expenses returns `{"currency": "AUD", "expenses": []}`, not 404.
- Every amount in every response is a string produced by `format_amount`. A test walks every
  response payload and asserts no JSON number appears anywhere an amount is expected, and
  that no key named `cents` exists in any payload.
- `POST /api/expenses` in `equal` mode creates one expense whose allocations sum exactly to
  the total, authored by the acting member, in the group's currency, with `created_at` equal
  to the request's single clock read. A test asserts the stored `ExpenseEvent` field by
  field.
- `weight` mode and `exact` mode each have the same test. `exact` amounts arrive as strings
  and are parsed with `parse_amount` before reaching `split_exact`.
- An `amount` that is a JSON number, not a string, is 400 `malformed_request` with a message
  saying amounts are strings. A test covers `12.50` and `1250`.
- An amount of `"0.00"`, a negative amount, an amount with three decimal places and an amount
  above `MAX_CENTS` are each 400 with the domain layer's own message.
- A `payer_id` that names no member of this group is 400 `malformed_request` naming the id,
  decided from the roster before any write, so no foreign key violation is ever reached. The
  same holds for every member id inside a split.
- A split naming a member twice, an empty member list, weights summing to zero and exact
  amounts that do not sum to the total are each 400 `invalid_split` carrying the resolver's
  message, including the "you are out by" figure the resolver produces for the last one.
- A `split.mode` that is not one of the three is 400 `malformed_request` naming the three.
- A failed `POST /api/expenses` writes nothing. A test asserts the expense count is unchanged
  after each rejection above.
- `GET /api/balances` returns one `net` entry per member of the group in roster order, using
  `Balances.net_for`, with `direction` in `{"owed", "owes", "settled"}` and a non-negative
  `amount`. A member the ledger has never seen appears as `"0.00"` and `"settled"`.
- `transfers` is `simplify_debts`' plan in its own order, with `from_member_id`,
  `to_member_id` and `amount` only, and no provenance. A settled group returns an empty list,
  which is a 200 and not a 404.
- A hand-built three-expense fixture asserts the exact net figures and the exact transfer
  list, with integer-exact amounts and no approximate comparison, per
  `.claude/rules/testing.md`.

## Out of scope

- **Any screen content.** No expense form, no feed rendering, no balances rendering, no
  member picker, no amount field. Tasks 10, 11 and 12 own those, and this task's only front
  end work is the API client, the auth gate and the boot wiring.
- **Any endpoint not in the table.** No settlement endpoints (tasks 14 and 15), no
  correction endpoint (task 17), no transfer drill-down payload (task 13), no staleness
  figures (task 16), no group or member creation, no linking, no password change, no "sign
  out everywhere", no user list, no health check and no metrics endpoint. Every one of them
  has an owner or a reason.
- **Transfer provenance in the balances payload.** Task 13 adds `payer_debts` and
  `receiver_credits`; `simplify_debts` already computes them, so it is a widening of one
  object and not a new endpoint.
- **Pagination, filtering, sorting or search on the feed.**
- **TLS, certificates, HSTS, a reverse proxy, a production WSGI server, a process manager, a
  container or any deploy pipeline.** Recorded as a gap above.
- **Trusted-proxy handling.** No `ProxyFix`, no `X-Forwarded-For`, no `Forwarded` parsing.
- **A Content Security Policy**, and any inline-script inventory or nonce mechanism.
- **CORS in any form.** One origin serves both halves, which is the whole design.
- **A second CSRF mechanism, a token library, a form library or a serialisation library.** No
  `flask-wtf`, `flask-cors`, `flask-login`, `flask-limiter`, `marshmallow`, `pydantic`,
  `sqlalchemy`, `gunicorn` or `waitress`.
- **Templates.** No Jinja rendering, no server-rendered HTML, no `templates/` directory. The
  shell is static files and the API is JSON.
- **`flask.session`, `SECRET_KEY`, signed cookies, JWTs and any client-held state.** Task 7's
  design is an opaque random token in a server-side table, and nothing here changes it.
- **Sliding session renewal, refresh tokens, remember-me, a device list and multi-factor.**
  Task 7 cut all of them.
- **Password reset, email verification, invites, onboarding and any outbound email.** The
  spec and task 7 cut them.
- **Roles, permissions, admins and owners.** Membership is the only authorisation.
- **Any change to the schema, `SCHEMA_VERSION`, `_SCHEMA_SQL` or the four event tables, and
  any migration.** Version 2 is what this task runs on, and the rate limiter is deliberately
  not a table.
- **Any change to how money, splits, balances, simplification, events, accounts or groups
  work.** `web.py` calls those modules and changes none of them.
- **Packaging `app/` into the wheel**, and running from an installed distribution.
- **Seeding demo data, fixtures or a "try it" mode.** Fake amounts in a money app are
  indistinguishable from wrong real ones, and task 18 owns the end-to-end fixture.
- **Offline entry, a request queue, background sync and conflict resolution.** The spec cuts
  them; an offline write must fail visibly.
